1

Agent与IM的关系本质

1.1 从通信协议到执行协议

IM（即时通讯）的本质是一套通信协议——它定义了人与人之间如何交换信息、如何建立会话、如何维持在线状态。从IRC到微信，从Slack到飞书，IM的核心能力始终是：消息路由、会话管理、在线感知、群组协调。

Agent的本质则是一套执行协议——它定义了意图如何被解析、任务如何被分解、行动如何被调度、结果如何被交付。从早期的RPA到如今的AI Agent，核心能力始终是：意图理解、任务编排、工具调用、结果交付。

关系本质

IM = 通信协议（人与人）  →  Agent = 执行协议（人与AI）

合并后的新物种

IM + Agent = 执行通信协议（人与AI+人与人协同）

当Agent与IM合并时，通信协议与执行协议的边界消失了。IM不再只负责"传话"，Agent也不再只负责"做事"——合并后的系统既理解"说什么"，也理解"做什么"。一个在钉钉群里@千问办公的请求，既是通信行为（发起对话），也是执行行为（触发任务编排）。

1.2 三层演化模型

Agent与IM的关系经历了三层演化，每一层都改变了两者之间的权力结构：

层级 关系模式 IM的角色 Agent的角色 代表产品
L1 嵌入 Agent嵌入IM 宿主/容器 插件/机器人 Slack Bot、企业微信机器人
L2 融合 IM能力Agent化 通信层+上下文源 执行层+编排器 千问办公、WorkBuddy
L3 合一 Agent OS取代IM 被吸收为子协议 成为操作系统 钉钉Agent OS（宣称）

L1嵌入阶段是最常见的"AI聊天机器人"模式——Agent作为IM的插件存在，用户在聊天窗口中@机器人获取服务。这个阶段，IM是绝对的主导者，Agent只是"聪明的对话机器人"，本质上和天气预报Bot没有结构性差异。

L2融合阶段是2026年正在发生的——IM的核心能力（消息路由、会话管理、群组协调）被Agent系统吸收，同时Agent的核心能力（任务编排、工具调用、工作流执行）也反向渗透到IM。千问办公的"25项企业IM能力"和WorkBuddy的"微信/企业微信多渠道连接"，本质上都是在做L2融合。

L3合一阶段是终态推演——当Agent成为工作的操作系统时，IM退化为通信子协议。钉钉2025年12月发布的"Agent OS"是最早的L3宣言，虽然实际能力仍在L2阶段，但方向已经明确。

1.3 一个关键类比：浏览器与操作系统

Agent与IM的关系，类比浏览器与操作系统最为贴切。早期浏览器只是操作系统上的一个应用；后来浏览器成为Web应用的运行环境；最终Chrome OS让浏览器本身成为操作系统。

类比映射：IM是浏览器（信息入口），Agent是Web应用（服务执行）。当Agent足够强大，它不再需要"嵌入"IM，而是吸收IM的通信能力，成为新的操作系统——Agent OS。

这个类比揭示了一个深刻的规律：当"执行层"的能力超过"通信层"，权力关系会反转。浏览器取代操作系统是因为Web应用生态足够强大；Agent取代IM是因为Agent的执行能力足够覆盖工作全流程。这就是为什么千问办公要把三个独立Agent产品合并，而不是简单地在钉钉里加个入口——执行层需要统一，否则通信层只是个"好看的壳"。

国内大厂Agent+IM合并全景

2026年8月，国内PC端AI办公智能体总访问量已达6000万次/月。五大厂——阿里、腾讯、字节、美团、百度——正在从不同路径合并Agent与IM，合并后的产品形态各不相同，但方向高度一致：Agent正在成为IM的"下一层"。

千问办公是2026年最具代表性的合并案例。三个独立Agent产品——本地桌面Agent QoderWork、云端工作流执行Agent MuleRun、企业IM协同Agent悟空——被合并为一个统一产品。这不是简单的功能整合，而是三种Agent执行模式的统一：

  • QoderWork基因 → 本地桌面Agent：直接操控用户电脑，完成文件管理、桌面应用操作
  • MuleRun基因 → 云端工作流执行：SaaS连接器驱动的自动化工作流
  • 悟空基因 → 企业IM协同：钉钉群内协作、消息路由、会话管理

合并后的产品定位"业内首款同时支持桌面端Agent、云端Agent、企业协同Agent的产品"，这本质上是宣布：执行层的统一才是合并的核心，IM只是执行层的一个通道。

关键动作：MyContext上下文基础设施（2026年8月18日开源）。阿里把分散在工作各处（钉钉聊天、文档、日历、审批）的数据加工成Agent可消费的上下文。这解决了Agent+IM合并的核心瓶颈——Agent需要IM中的上下文才能真正执行任务，而不仅仅是"接收消息"。

值得注意的是，阿里早在2025年12月就通过钉钉发布了"Agent OS"——"全球首个工作智能操作系统"。虽然当时的实际能力更接近L2融合阶段，但这个定位表明阿里理解了终态方向：钉钉要从IM进化为Agent OS，IM能力成为Agent OS的通信子协议。

  • 核心差异化：把Agent封装进腾讯文档、微信和企业微信等现有工作流——用户无需"打开一个Agent应用"，Agent就在日常使用的工具中

字节的Agent+IM合并路径是最"激进"的：不合并产品，而是合并产品线。2026年7月30日，飞书与豆包产品线正式融合，AI业务线重组。这意味着豆包的AI能力（3.45亿月活背后的大模型能力、用户习惯、交互模式）直接注入飞书的企业IM生态。

  • 路线特点：AI能力直接嵌入工作流——用户在飞书里自然地使用AI，不需要"开一个Agent"

字节路径的本质是"AI能力渗透"而非"产品合并"。这更接近L1→L2的渐进式演化：先把Agent能力嵌入IM（L1），再逐步让IM的能力被Agent化（L2）。与阿里的"一步到位三合一"相比，字节路径更温和，但可能也更可持续——用户不需要面对"新的产品"，只需要发现"飞书变聪明了"。

海外Agent+IM融合路径

海外市场Agent+IM的融合路径与国内有显著差异。国内以"大厂内部合并"为主旋律——阿里合并三产品、字节整合豆包飞书；海外则以"Agent平台接入第三方IM"为核心模式——OpenAI的Workspace Agents从ChatGPT和Slack双入口启动，Anthropic的Claude Tag直接嵌入Slack频道。这种差异反映了企业软件生态的结构性不同：国内是"大厂即生态"，海外是"开放平台+IM作为基础设施"。

Anthropic的Agent+IM融合策略有三个鲜明特点：

4

合并的底层逻辑

Agent与IM的合并不是偶然，而是技术、市场、用户三重力量共同作用的结果。本章从驱动力、阻力、关键变量三个维度拆解合并的底层逻辑。

4.1 驱动力：为什么必须合并？

\ud83d\ude80

驱动力1：上下文闭环

Agent的最大瓶颈不是"能不能做"，而是"知不知道做什么"。企业工作场景中，80%以上的任务上下文存在于IM对话、群聊、文档评论中。Agent如果不能访问IM中的上下文，就像一个没有通讯录的手机——硬件再强也拨不出电话。合并是Agent获取工作上下文的唯一路径。

\ud83d\udc65

驱动力2：协同效应

Agent不是孤岛——一个Agent执行完任务，结果需要通知团队、流转到下一个环节、触发下一个Agent。IM天然提供了协同基础设施：消息路由、群组机制、在线状态、通知推送。没有IM的Agent是"个体户"，有IM的Agent是"企业员工"。

\ud83d\udcca

驱动力3：用户习惯

企业用户每天在IM上的时间占工作总时长的40%以上。让Agent"住"在IM里，比让用户"打开"一个Agent应用更符合使用习惯。WorkBuddy的非开发者用户暴增、Codex非开发者增速3倍于开发者——这些数据都在验证一个判断：Agent的规模化采用必须"降维"到IM场景。

\ud83d\udcb0

驱动力4：商业模式

单独的Agent产品难以为继——用户获取成本高、留存率低、付费意愿不确定。但IM+Agent的组合可以：1）用IM的日活保住用户粘性；2）用Agent的执行能力创造差异化价值；3）用组合定价（IM免费+Agent付费）降低付费门槛。腾讯WorkBuddy的低价策略（每百万tokens输入1元/输出4元）就是这个逻辑的体现。

核心矛盾

Agent+IM合并的核心矛盾是：Agent需要"全量上下文"才能执行好任务，但IM中的"全量上下文"包含大量敏感信息和噪音。这个矛盾不是技术问题，而是治理问题——谁有权决定Agent能访问什么？谁来审计Agent看了什么？谁来为Agent的误操作负责？阿里的MyContext只解决了"如何加工上下文"，但没有解决"谁授权加工"。这是合并路径上最大的结构性障碍。

4.3 关键变量：决定合并速度的五个因素

以下五个变量将决定Agent+IM合并的速度和深度：

1. 模型能力
75%

大模型的工具调用能力（function calling）和长上下文理解能力已达到较高水平，但自主决策和错误恢复能力仍有差距

2. 上下文基建
35%

阿里的MyContext是首个系统性方案，但80%企业仍在用"复制粘贴"方式给Agent喂上下文

3. 安全治理
25%

Agent权限模型、行为审计、责任归属等治理框架尚未成熟

4. 非技术用户
50%

WorkBuddy/Codex的非开发者用户增速已超过开发者，但使用深度（Task Completion Rate）仍低

5. 算力成本
55%

模型推理成本下降速度够快，但Agent的全链路成本（上下文处理+多步推理+工具调用）仍高

判断：2026-2027年是Agent+IM合并的关键窗口期。模型能力已就绪，上下文基建刚起步，安全治理尚处早期——这三个变量决定了合并的深度。谁能在"上下文基建"和"安全治理"上率先突破，谁就能在L2→L3的跨越中占据先手。阿里的MyContext是上下文基建的第一步，但安全治理方面目前没有系统性的解决方案出现——这是一个巨大的结构性空白。

5

终态推演——Agent OS

当Agent与IM完成合并，终态产品是什么样的？它不是"更好的IM"也不是"更强的Agent"——它是一个全新的品类：Agent OS，工作智能操作系统。

5.1 Agent OS的定义与能力框架

Agent OS = 工作智能操作系统

Agent OS = 执行层（Agent Runtime）+ 通信层（IM Protocol）+ 上下文层（Context Infra）+ 工具层（Skill/Connector）+ 治理层（Permission/Audit）

Agent OS的五层架构：

层级 能力 对标传统操作系统 当前最接近的产品
执行层 Agent Runtime：任务分解、编排、执行、错误恢复 进程管理+调度器 Codex、Claude Code
通信层 IM Protocol：消息路由、会话管理、群组协调、在线感知 网络栈+IPC 钉钉、Slack
上下文层 Context Infra：工作数据的采集、加工、检索、供给 文件系统+虚拟内存 阿里MyContext
工具层 Skill/Connector：可调用的外部工具和SaaS连接器 系统调用+驱动程序 WorkBuddy Skill、Workspace Agents连接器
治理层 Permission/Audit：权限控制、行为审计、成本计量、责任归属 安全子系统 尚无成熟方案

这个类比揭示了Agent OS的本质：它不是一个"智能聊天工具"，而是一个运行在云端的工作操作系统。就像Windows管理进程、文件、网络一样，Agent OS管理Agent、上下文、通信、工具。IM是Agent OS的"网络栈"——它提供通信能力，但不是操作系统的全部。

5.2 Agent OS的四个核心体验

Agent OS的终态体验可以用四个词概括：无处不在、团队原生、自我进化、成本透明。

\ud83c\udf10

无处不在

Agent不绑定单一入口。从IM群聊、文档编辑器、日历、代码IDE、甚至邮件——任何工作场景都是Agent的工作场景。千问办公的"桌面端+网页端+钉钉嵌入"、Workspace Agents的"ChatGPT+Slack双入口"，都是在逼近"无处不在"的终态。

\ud83d\udc65

团队原生

Agent不是个人工具，而是团队资产。Workspace Agents的"named, shared, persistent agents"是最接近团队原生的设计——Agent有名字、可以被分享、行为持久化。在IM场景下，团队原生意味着：一个群里的Agent可以代表团队行事，而不仅仅是"群里的一个机器人"。

\ud83d\udd04

自我进化

Agent OS中的Agent不是静态配置的，而是根据团队的使用模式不断学习和优化。一个团队用Agent写了三个月周报后，Agent应该"进化"出团队最习惯的周报格式和流程——这需要Agent具备记忆和自优化能力。

\ud83d\udcb0

成本透明

Agent OS的使用成本必须可计量、可归因、可优化。Claude Managed Agents的$0.08/会话小时、某公司AI洞察的Token积分制——都在逼近"成本透明"的终态。当Agent成为基础设施，成本不可见意味着资源不可控，资源不可控意味着规模化不可能。

5.3 Agent OS的三种演进路径

基于当前国内外产品形态，Agent OS有三条可能的演进路径：

路径A：Agent吃IM

Agent产品为核心，吸收IM能力成为Agent OS。

代表：阿里千问办公（三合一）。优势：执行层统一、能力完整；劣势：用户需要迁移到新产品。

路径B：IM吃Agent

IM生态为核心，Agent能力渗透进IM成为Agent OS。

代表：腾讯WorkBuddy、Google Gemini in Workspace。优势：零迁移成本、用户基数大；劣势：执行层碎片化、Agent编排困难。

路径C：平台化融合

Agent平台+IM作为基础设施，开放融合。

代表：OpenAI Workspace Agents + Slack。优势：生态开放、竞争驱动创新；劣势：依赖第三方IM、体验一致性难保证。

三条路径最终都指向Agent OS，但路径的选择决定了产品的形态和节奏。路径A（Agent吃IM）最激进，最快达到L3，但用户迁移成本最高；路径B（IM吃Agent）最温和，用户零迁移，但L2→L3的跨越最难；路径C（平台化融合）最开放，但需要Agent平台足够强大才能"主导"融合。

终态判断

Agent OS的终态不是"三选一"，而是三种路径并存，各自服务不同市场。路径A（Agent吃IM）更适合技术敏感型企业——他们愿意迁移到更好的Agent产品；路径B（IM吃Agent）更适合传统企业——他们不想换工具，只想让现有工具变聪明；路径C（平台化融合）更适合海外市场——那里IM是公共基础设施，Agent是增值服务。中国市场更可能走向A和B的混合——大厂各自用最擅长的方式合并，最终形成"Agent OS百家争鸣"的局面。

6.1 AI洞察的当前位置

AI洞察的核心优势：与阿里、腾讯、字节的Agent产品相比，AI洞察有两大结构性优势：1）Work+Code双形态——覆盖非开发者和开发者两类用户，与OpenAI的Codex（开发者）+Workspace Agents（非开发者）组合策略一致；2）AgentOS内核+自进化——2.0的Agent SDK和自进化能力是其他国内产品尚未明确的方向，这意味着AI洞察在"Agent作为操作系统"这条路上走得最远。

6.2 AI洞察走向Agent OS的路径推演

AI洞察走向Agent OS的最优路径是"路径A+：Agent吃IM，但保留IM作为独立交互层"。这与阿里的千问办公路径类似，但有一个关键差异：AI洞察不需要"合并三个独立产品"（因为1.0和2.0已经是统一产品），它需要做的是吸收KIM的通信能力。

阶段一：KIM深度融合（2026 Q3-Q4）

  • Agent在KIM群中不仅"被动响应@提及"，还能"主动推送"任务进度、异常告警、完成通知
  • KIM群聊历史成为Agent的上下文源——Agent可以回溯群聊中的决策、任务分配、讨论结论
  • 群聊中的文档、链接、图片自动进入Agent的知识库
  • KIM的"会话"概念被重构——每个KIM会话都是一个Agent工作空间

阶段二：上下文基建（2027 Q1-Q2）

  • 建设"某公司MyContext"——将KIM聊天、Docs文档、日历、审批、OKR等全量工作数据加工为Agent可消费的上下文
  • 上下文分级：公开上下文（群聊公告）、团队上下文（项目文档）、个人上下文（私聊历史）——不同级别的Agent可访问不同级别的上下文
  • 上下文蒸馏：从噪音大的原始数据中提取高信噪比的决策上下文，避免Agent被信息淹没
  • 上下文版本化：工作上下文是动态的，Agent需要理解"这个决策的上下文在两周前是什么，现在是什么"

阶段三：Agent OS成型（2027 H2）

  • KIM退化为Agent OS的通信子协议——用户不再"打开KIM发消息"，而是"在Agent OS中通信"
  • Work形态和Code形态统一为Agent OS的两个"视图"——不是两个独立产品，而是同一个Agent OS的不同交互面
  • Agent平台和PDE Agent作为Agent OS上的"垂直应用"——类比手机OS上的App
  • Skill市场从"57→5000+"进化为Agent OS的"App Store"——Skill是Agent OS上的可安装能力包
  • Token积分制进化为Agent OS的"资源管理器"——可以精确计量每个Agent、每个Skill、每个用户的资源消耗

6.3 AI洞察 vs 竞品：差异化定位

在Agent OS的终态竞争中，AI洞察的差异化应该建立在三个独特优势上：

优势1：自进化内核

AI洞察 2.0的Agent SDK + 自进化能力是国内Agent产品中唯一的"学习型"架构。千问办公和WorkBuddy的Agent是"配置型"的——用户配置Agent做什么，Agent就做什么；AI洞察的Agent是"进化型"的——Agent根据使用模式不断优化自己的行为。这个差异在L3阶段会放大：当Agent OS需要管理数万个Agent时，手动配置不再可行，自进化是唯一的扩展方式。

优势2：垂直Agent生态

Agent平台（研发&质量）和PDE（创意→设计→vibe→部署）是AI洞察独有的垂直Agent。这些垂直Agent既是Agent OS上的"杀手级应用"，也是其他通用Agent产品无法复制的护城河——通用Agent可以做"什么都还行"，但垂直Agent可以做"这件事非常好"。Agent OS的终态不是"一个万能Agent"，而是"一个操作系统+无数垂直Agent"。

优势3：内部生态闭环

某公司有KIM（IM）、Docs（文档）、内部工具链（开发/测试/运维）——这是一个完整的企业工作生态。AI洞察不需要像OpenAI那样"接入第三方Slack"，也不需要像阿里那样"合并三个独立产品"——所有组件都在一个组织内部，天然具备"合并"的条件。美团的CatPaw证明了内部闭环的优势（3万Agent最大规模落地），AI洞察可以复刻这个路径，但起点更高（Agent OS内核已就绪）。

C

结论与建议

核心结论

本次调研的五个核心研究问题，结论如下：

结论1：Agent与IM的关系本质是"通信协议→执行协议"的演化

IM定义了人与人如何交换信息，Agent定义了意图如何被执行。合并后的新物种——"执行通信协议"——既理解"说什么"也理解"做什么"。这不是功能叠加，而是协议层融合。

结论2：国内大厂正在用两种路径合并Agent和IM——"Agent吃IM"和"IM吃Agent"

阿里千问办公（三合一合并）走"Agent吃IM"路径，腾讯WorkBuddy（工作流封装）走"IM吃Agent"路径，字节豆包+飞书（产品线融合）走中间路线。三条路径的终态都是Agent OS，但节奏和用户体感差异显著。

结论3：海外的Agent+IM融合建立在"开放平台"之上，与国内的"大厂即生态"结构不同

OpenAI和Anthropic选择Slack（第三方IM）作为Agent入口，而国内每家都有自己的IM生态。这决定了海外竞争的焦点是"Agent能力"，国内竞争的焦点是"生态整合体验"。

结论4：合并的驱动力是"上下文闭环+协同效应+用户习惯+商业模式"，阻力是"数据基建+安全治理"

66%企业认为数据基础设施拖慢Agentic AI落地，但80%企业将"用好自家数据驱动AI"列为优先事项——需求和供给之间存在巨大缺口。阿里的MyContext是上下文基建的第一步，但安全治理的系统性方案尚未出现。

结论5：AI洞察具备走向Agent OS的三大独特优势，但上下文层和治理层是关键短板

自进化内核、垂直Agent生态、内部生态闭环——这三大优势是AI洞察在Agent OS终态竞争中的护城河。但上下文基建和安全治理的短板需要优先补齐，否则"Agent吃IM"的路径会因为"Agent吃不饱"（上下文不够）和"Agent不可信"（治理缺位）而受阻。

关键建议

  1. 立即启动"某公司MyContext"上下文基建项目。对标阿里8月18日开源的MyContext，将KIM聊天、Docs文档、日历、审批等全量工作数据加工为Agent可消费的上下文。这是Agent+IM合并的核心瓶颈，也是AI洞察最大的短板。建议在2026 Q4前完成MVP。
  2. 加速KIM深度集成，从"被动响应"到"主动协同"。当前Agent在KIM中只能被动响应@提及，需要进化为：1）主动推送任务进度和异常告警；2）回溯群聊历史获取上下文；3）将KIM会话重构为Agent工作空间。这是L2融合的核心体验升级。
  3. 将Token积分制升级为Agent资源管理器。当前积分制只解决成本计量，需要扩展为：1）每个Agent/每Skill/每用户的资源消耗可归因；2）资源预算可配置和可预警；3）资源使用可优化（缓存命中率、上下文压缩率等指标可视化）。这是Agent规模化部署的必要条件。
  4. 安全治理框架提前布局。Agent权限模型（Agent可访问什么数据）、行为审计（Agent做了什么操作）、责任归属（Agent出错谁负责）——这三个问题在Agent规模小时可以"人治"，规模大了必须"法治"。提前布局可以在L2→L3跨越时占据先手。
  5. 强化"自进化"作为AI洞察的核心差异化叙事。国内所有Agent产品都在讲"更智能"、"更方便"，但没有一家在讲"Agent会学习你的习惯、会自我优化"。AI洞察 2.0的自进化能力是真正独特的——但需要在产品体验中让用户"感受到"进化，而不仅仅是一个技术指标。

终态展望

Agent OS不是一个遥远的概念——钉钉在2025年底就已经发布了"Agent OS"的品牌宣言，虽然实际能力还在L2阶段。但方向已经明确：IM正在从"工作的入口"进化为"Agent OS的通信层"，Agent正在从"AI助手"进化为"工作操作系统"。

这场合并的终局不是"谁吃掉谁"，而是"一个新物种的诞生"。就像智能手机不是"更好的电话"，而是"一个全新的计算平台"；Agent OS也不是"更好的IM"或"更强的Agent"，而是一个全新的工作操作系统——它管理Agent、上下文、通信、工具、治理，就像Windows管理进程、文件、网络、驱动、安全。

AI洞察有走到这个终态的结构性优势——自进化内核、垂直Agent生态、内部闭环。但优势只有在行动中才有效。2026-2027年是Agent OS的窗口期，上下文基建和安全治理是关键解锁，KIM深度融合是当前最优先的P0行动。
