01 · 执行摘要

0. 执行摘要：先给决策者的六句话

  1. AI Native SDLC 的最小管理单元不再是“代码提交”，而是“可信变更”：一个变更必须同时有意图、约束、验证证据、风险归属和生产反馈入口。
  2. 代码生成已从主要瓶颈退居中间环节。真正限制组织吞吐的是意图澄清、验证、审查、发布治理和事故回流；只扩张 Agent 会把排队与风险推向下游。
  3. 模型能力不是组织能力。模型决定上限；Context、Harness、Evals、权限与观测共同决定生产环境中的可用下限。
  4. 人机分工应从“人写、AI 辅助”改为“Agent 执行、人定义和承担”：人类拥有目标、架构取舍、风险接受和生产责任；Agent 负责研究、生成、执行和提交证据。
  5. 治理必须分层：可容错的规则进入 Context/Skill；绝不可违反的规则进入权限、沙箱、Hook、CI 和审批门禁。不要把门锁写成提示词。
  6. 某公司的下一步不是再加一个 Coding Agent，而是把 Agent平台、AI洞察 Code、AgentOS、Agent 评测与 AI 度量收敛成“可信变更工厂”。先打穿一条低—中风险价值流，再以证据扩大自治半径。

本报告的核心判断：未来 12—24 个月的工程组织差距，首先不是“谁的 Agent 写码更快”，而是谁的验证吞吐量更高——即在不同比例增加人工审查的前提下，安全地让更多变更通过可信验证、进入生产并被持续学习。

02 · 问题界定

1. 问题界定：为什么现在要重做 SDLC

1.1 现象：局部效率很高，端到端交付未必变快

AI Coding 已经把“从想法到可运行代码”的时间压缩到小时级甚至分钟级。但企业的交付价值流不是单一 Build 环节，而是：

意图 → 方案 → 实现 → 验证 → 审查 → 发布 → 运行 → 反馈

当实现环节加速，而其余环节仍按人工节奏运转，结果通常是：

  • 更多 Agent 产物堆积在测试、CR、安全与发布队列；
  • 为了不堵塞而降低审查标准，缺陷与安全风险进入生产；
  • 工程师从编码瓶颈变成“AI 输出复读机”；
  • 更多代码、更多 PR、更多 Token，却不一定有更多业务结果。

因此，不应再以“生成代码行数、调用次数、PR 数”为主要成功指标。应当衡量：

从一个被确认的业务意图，到一个在生产环境被验证的业务结果，所需的总时间、总返工、总人工注意力、总成本和后续维护负担。

1.2 本报告的边界

本调研讨论两类相互关联但不可混同的问题：

对象 典型问题 验证重点
用 Agent 开发普通软件 Agent 生成的变更能否安全合并、上线和维护？ 测试、架构约束、CI、审查、发布门禁
开发 Agent 产品本身 Agent 是否正确使用工具、上下文和策略，并完成任务？ Evals、轨迹、模拟、用户反馈、成本与延迟

前者以 Anthropic 的 AI-Native SDLC 为代表；后者以 LangChain 的 Agent Development Lifecycle 为代表。两者共享治理基础设施，但质量模型不同。

3.2 共同结论：五条正在收敛的行业判断

  1. 代码、测试和文档的初稿成本快速下降；
  2. 组织瓶颈迁移到需求、验证、审查、部署和治理；
  3. 模型之外的 Context 与 Harness 决定真实工程结果；
  4. 测试、Evals、轨迹和生产反馈必须构成闭环；
  5. 人类角色从主要实施者转向意图定义者、系统设计者和风险责任人。

这五点构成了“AI Native SDLC”最小共识。其余差异，主要是各家从产品、平台或组织的不同切口展开。

05 · 本质洞察

4. 本质洞察：从代码生产系统到可信变更系统

4.1 第一层：代码不再是唯一稀缺物

过去，代码实现需要大量专业工时，SDLC 的流程、角色分工和审批节奏都围绕“如何让稀缺工程师高效写代码”设计。

现在，Agent 让实现初稿趋于廉价。代码仍重要，但它更像一个中间产物：它必须被意图约束、被测试验证、被风险治理、被生产结果校准。

4.2 第二层：真正被规模化的是“可信变更”

本报告建议将 AI Native SDLC 的最小交付单元定义为：

可信变更（Trusted Change）= 明确意图 + 可执行约束 + 可复现实现 + 独立验证证据 + 明确责任归属 + 可回流生产反馈。

它不是“多写几份 Markdown”。制品的唯一价值，在于它能被下一步消费：

制品 解决的决策 必须被谁消费 无法消费时的判断
Intent 为什么做、谁受益、什么不做 产品/业务 Owner、设计 Agent 只是需求文书
Spec 约束、接口、非功能要求与待决问题 技术 Owner、实现 Agent 只是格式化 PRD
Plan 改哪些文件、怎么改、如何证明 实现者、审查者 只是任务拆分记录
Diff + Test Evidence 实现是否满足约束 CI、验证 Agent、Reviewer 只是代码堆积
Review / Release Record 剩余风险谁接受 Code Owner、Release Owner 只是签字痕迹
Production Trace / Incident 真实结果与失败模式 Eval、Skill、规则维护者 只是事故档案

4.3 第三层：真正稀缺的是“压缩不确定性的能力”

AI Native 组织的竞争力不取决于谁有更多生成能力，而取决于谁能以更低的人类注意力成本，将不确定性持续压缩为可信决策。

可以把能力演进分为四层：

阶段 稀缺物 核心能力 典型失败
手工编码 实现能力 研发人力和协作 需求排队、开发慢
AI 辅助编码 局部人机协同 Prompt、IDE、局部自动化 个人提效，组织无感
AI Native 交付 可信变更能力 制品、验证、治理、闭环 代码暴增，审查与事故也暴增
自学习工程系统 组织学习速度 生产反馈→Eval/Skill/策略 问题反复出现，经验不复利

4.4 类比：机场，而不是更快的飞机

Agent 是更快的飞机。机场吞吐却取决于空管、跑道、安检、调度、登机口和异常处置。

如果只增加飞机数量，得到的是更长的滑行队列和更高的事故概率。AI Native SDLC 的任务，是把整个机场重建为能够安全处理更高流量的系统。

06 · Context & Harness

5. 核心框架一：Context 与 Harness 是工程能力转换器

5.1 Context Engineering：不是塞更多信息，而是在正确时机提供高信号信息

一个生产级 Agent 的上下文通常包括：

  • 需求与验收条件；
  • 代码库、架构边界与历史决策；
  • 领域规则、安全和合规策略；
  • 工具、API、MCP 服务与工具使用语义；
  • 会话状态、长期记忆和检索知识；
  • 可运行的构建、测试、截图、检查命令；
  • 任务拆分、角色分工和审批状态。

上下文工程的目标不是“信息越多越好”，而是同时解决四个问题：正确性、相关性、可审计性、最小暴露面。

上下文问题 结果 治理动作
不足 Agent 猜测、重复犯错 建立规则文件、知识索引、任务模板
过载 噪声、成本、注意力稀释 分层加载、任务化检索、过期治理
不可追溯 无法解释决策来源 记录版本、来源、调用轨迹
包含敏感数据 数据泄漏与越权 最小权限、脱敏、环境隔离、短期凭据

5.2 Harness Engineering：模型之外的执行系统

Harness 是把模型能力转化为稳定工程结果的环境。至少包含六层：

层 关键能力 失效后果
任务层 Intent、Spec、Plan、验收条件 Agent 做错问题
知识层 规则、架构、示例、检索 Agent 依据错误/不完整
工具层 MCP/API/命令语义、幂等性 Agent 调错工具或重复操作
执行层 Runtime、状态持久化、Sandbox 任务中断、环境污染、越权
控制层 权限、Hooks、审批、CI 不可接受的动作发生
学习层 Trace、Evals、反馈、度量 同类失败不断重演

判断：同一模型在 Demo 中表现优异、在企业生产中不稳定，常常不是“模型变笨”，而是 Harness 没有给它地图、护栏和仪表盘。

07 · 治理与责任

6. 核心框架二：Skills、Hooks 与人类责任的三层治理

6.1 Skills 与 Hooks：建议性控制和确定性控制不能混淆

控制类型 适用内容 实现例子 失败代价
Context / Prompt 临时任务偏好、写作风格 “优先复用现有模块” 一般可纠正
Skill 必须一致应用的流程知识 API 评审、安全检查、测试规范 应显著降低违例概率
Hook / Policy / CI 绝不可违反的规则 禁读密钥、禁止改受保护目录、生产授权 必须技术上阻断
Human Gate 价值判断、风险接受、例外授权 架构取舍、核心业务发布 必须由命名责任人承担

一句话：可建议的事交给 Skill；必须成立的事交给系统；无法形式化的权衡留给人。

6.2 Delegate / Review / Own：从“Human in the Loop”到责任可审计

责任关系 典型任务 人类责任 不可省略的证据
Delegate 代码初稿、测试初稿、资料检索、低风险修复 定义边界和验收 输入、工具轨迹、产物
Review 方案、复杂变更、性能/安全分析 复核完整性与异常 风险清单、验证结果、评审意见
Own 产品意图、架构取舍、风险接受、生产授权 最终决定与签署 命名 Owner、审批与审计记录

真正的变化不是“人退出回路”，而是人类注意力从逐行实施迁移到高杠杆判断与例外处置。

6.3 风险分层自治矩阵

变更等级 示例 Agent 权限 人类门禁 退出条件
L0 探索 原型、一次性脚本、内部试验 高自主，可快速试错 仅环境边界 不进入生产资产
L1 低风险 文档、测试补充、样式、低影响缺陷 自动实现 + 自检 + PR Owner 合并 测试/检查全绿
L2 中风险 普通业务功能、跨模块重构 先 Plan 后执行，独立验证 Plan + PR 审批 Eval/CI/评审通过
L3 高风险 身份、支付、数据、基础设施 只读分析或受控执行 架构/安全/发布三类授权 明确回滚与审计完整
L4 受监管/不可逆 高敏数据、关键生产变更 默认不可自治 双人或变更委员会 人工授权、预案验证

自治等级不应由“模型有多强”单独决定，而应由风险、可逆性、验证强度、历史稳定性和审计要求共同决定。

08 · 验证与 Evals

7. 核心框架三：验证从阶段变成语言

7.1 为什么测试要前移并独立

Agent 同时写实现与测试时，可能把同一个错误假设写进两边；更危险的是它可能通过弱化断言、删除失败测试或过度 Stub 来“制造通过”。

生产级验证至少应分为三层：

层 要验证什么 方法 责任
确定性约束 权限、格式、编译、静态规则 CI、Lint、Policy-as-Code 平台自动执行
任务正确性 功能、边界条件、体验、性能 单测/集成测试/截图/回放 实现 + 独立验证
业务有效性 是否解决真实用户问题 业务指标、用户反馈、灰度实验 产品/业务 Owner

三层不能相互替代。CI 全绿不代表业务正确；用户满意也不能成为绕过安全门禁的理由。

7.2 Evals 是 Agent 时代的回归资产

对于 Agent 产品或 Agent 配置（Prompt、Skill、Tool、Model、Context），需要把“这次看起来不错”变为“版本变化后仍可比较”。

初始 Eval 集不必完美，可从 20—50 个真实任务开始；关键是形成制度：

  1. 每次模型、Prompt、Skill、Tool 或策略变化都跑回归；
  2. 每次线上事故、用户纠正或高价值失败都进入样本集；
  3. 每个 Eval 都应有明确评分：事实正确、策略遵循、工具选择、效率、人工接管等；
  4. 观察 Eval 通过率，更要观察生产失败进入 Eval 的时滞。

最有价值的 Eval，不是实验室中最漂亮的样本，而是生产中最难、最贵、最容易重复的失败。

7.3 Trace：Agent 可观测性的基础单位

传统监控常回答“服务是否 200、延迟是否异常”。Agent 的任务可能技术上成功却业务上失败，因此还必须回答：

  • 它读了什么上下文？
  • 调了什么工具？为什么调？
  • 是否跳过审批、走错路径、使用了不可靠来源？
  • 用户是否纠正了它？花了多少步和成本才完成？

一个可用 Trace 至少应关联：输入、上下文版本、模型/配置、工具调用序列、输出、审批、用户反馈、任务结果与成本。

09 · 反模式

8. 反模式：最容易把 AI Native 做成“更快的混乱”的六种方式

反模式 表面现象 深层问题 纠偏动作
只买 Coding Agent 代码量与 PR 数上升 验证、审查与发布未升级 先补验证证据和门禁
制品仪式化 多了 intent/spec/plan 制品不被下一步消费 每份制品绑定决策、Owner、自动动作
用 Prompt 管安全 “请不要读密钥” 建议性规则无法保证 权限、Sandbox、Hook、短期凭据
多 Agent 盲目并发 WIP 与产出都变多 合并冲突与审查队列爆炸 按依赖拆分，WIP 上限，独立 Worktree
把 Eval 当业务真相 通过率很高 对固定样本过拟合 加入真实反馈与业务指标
把 Token 当唯一成本 单次调用很便宜 人审、返工、事故、维护成本被隐藏 衡量每个接受变更的综合成本

9.1 不是新增一条产品线，而是把现有能力收敛成一个操作系统

结合当前已知产品与组织分工，可形成如下映射：

运行时与安全 AgentOS Runtime、Gateway+安全 管理态 Hook、生产策略、身份与审计统一
验证与评测 Agent 评测、Agent平台 测试域能力 真实任务 Eval、独立验证 Agent、配置回归
观测与学习 Agent 观测、AI 度量、效能 Data Agent Trace 标准、人工纠正采集、失败→Eval 自动化

关键判断：这些能力若分别作为产品卖点，会形成碎片；若围绕“可信变更”统一制品、策略、Trace 与度量，才会形成系统护城河。

9.2 建议的北极星：可信变更吞吐量，而非 AI 代码量

建议为 AI x 研发效能建立一个组合北极星，而不是单一指标：

Trusted Change Throughput（TCT）：在既定风险等级下，单位时间内完成“验证充分、审计完整、生产稳定”的变更数量。

需要配套四组护栏：

维度 主指标 护栏指标
流动效率 Intent→生产验证时长 WIP、审查等待、部署等待
质量可靠 首次 CI/Eval 通过率 返工轮次、缺陷逃逸、变更失败率、MTTR
Agent 质量 任务完成率、工具正确率 人工纠正率、无效循环、上下文/工具失败
治理与成本 每个接受变更的综合成本 越权拦截、审计完整率、例外率、Token 成本

反向校验：若 AI 代码贡献率上升，而 Intent→生产时长、返工率、缺陷逃逸或人工审查时间没有改善，则不能宣布组织级提效。

9.3 对 L1—L4 研发成熟度的重新解释

成熟度 不应只定义为 更应定义为
L1 AI Coding 是否使用代码补全 Agent 能否在局部任务完成受控生成
L2 AI 辅助开发 AI 参与了多少环节 是否具备 Plan、可运行验证与人工 Review
L3 AI 协同开发 多 Agent 是否协作 是否存在共享制品、独立验证、风险分层自治
L4 AI 自主开发 Agent 是否能端到端跑 是否在限定风险域内形成可审计、可回滚、自学习闭环

这一定义能避免把“更高的自治”误解为“更少的人”。L4 的前提是更强的约束、观测和责任系统。

11 · 90 天路线图

10. 推荐落地路线：90 天打穿一个最小闭环

原则：先选价值流，不先选平台功能

选择一个高频、低—中风险、可度量、可回滚的真实场景，例如：测试补充、低风险缺陷修复、依赖治理、内部工具小功能或文档与代码一致性修复。不要一开始挑支付、身份、核心数据链路。

10.1 第 0—30 天：建立“可验证的 Agent 工作单元”

目标：任何 Agent 任务都能说明目标、边界、运行过什么检查、产出什么证据。

动作 交付物 验收标准
选定试点价值流和风险等级 场景清单 + L1/L2 边界 明确不允许 Agent 做什么
建立最小任务模板 intent / acceptance / owner 需求、约束、验收、Owner 均非空
统一一键验证命令 build/test/lint/关键检查 本地与 CI 均可执行、失败非零退出
建立轻量规则文件 项目上下文、架构、常见错误 只留高信号内容，有 Owner 和版本
开启基础 Trace 任务输入、工具、结果、人工修正 可回放 80% 以上试点任务

本阶段不追求：全自动发布、多 Agent 编排、复杂知识库。

10.2 第 31—60 天：形成制品链与确定性边界

目标：Agent 在代码前提交计划，在人类前提交验证证据；不可违反的规则不可绕过。

动作 交付物 验收标准
引入 Intent→Plan→Diff→Evidence 链 制品模板与关联 ID 审查可追溯意图、计划与验证
把重复规则写成 Skills 3—5 个高频 Skill 触发覆盖率、违例率可观测
把红线写成 Hooks/Policy 密钥、受保护路径、生产命令 可复现拦截，不能靠 Prompt 绕过
引入独立验证 Verifier Agent 或独立会话 不与实现者共享关键假设
设置风险自治矩阵 L0—L3 操作权限表 每类操作有明确 Owner 和出口

10.3 第 61—90 天：建立 Eval 与反馈回流

目标：将真实失败变成永久资产，并据此决定是否扩大自治。

动作 交付物 验收标准
建立初始真实任务 Eval 集 20—50 个案例 + 评分 配置变更可回归比较
事故/人工纠正回灌 失败→Eval/Skill/Hook 流程 高价值失败 7 天内入库
建立试点仪表盘 四维指标看板 可按风险、团队、任务类型切片
复盘自治扩大条件 L1→L2/L2→L3 准入标准 不是靠主观感觉升级

10.4 自治升级的准入条件（建议）

从 L1 升到 L2，至少连续四周满足：

  • 关键任务首次验证通过率达到团队基线以上；
  • 无 P0/P1 越权事故；
  • 任务 Trace 与证据完整率 ≥ 95%；
  • 人工返工率不高于人工实现基线；
  • 关键失败均有 Owner 与回灌动作。

具体阈值需以试点团队基线校准，不能照搬行业数字。

12 · 关键决策

11. 组织与产品决策：现在必须回答的五个问题

  1. 可信变更的唯一 ID 和唯一事实源是什么？ 需求系统、代码仓、评测平台与 Agent Trace 如何联通？
  2. 哪些规则是建议、哪些规则必须阻断？ 谁拥有规则，谁批准例外，规则如何随业务变化更新？
  3. 谁对 Agent 产物承担最终责任？ 必须从“某团队在看”落实到命名 Owner 与授权范围。
  4. 生产失败如何成为下一次能力增量？ 从失败发现到进入 Eval、Skill 或 Hook 的时滞是多少？
  5. 扩张 Agent 并发前，验证与审查能力是否已扩张？ 没有，就先别扩张生成侧。
13 · 趋势判断

12. 最终判断与趋势推演

12.1 未来 12—24 个月的竞争焦点

演进 已经发生 下一步竞争
生成 代码、测试、文档初稿成本下降 生成质量将快速趋同
验证 CI、静态检查、评测开始自动化 验证吞吐量与证据质量
编排 多 Agent、工作流、任务分解成熟 人类注意力如何只投入例外
学习 Trace、反馈、Eval 回灌兴起 失败能否持续变成组织资产

12.2 结论

AI Native SDLC 不是“让 Agent 替人写软件”，而是建立一种新的工业能力：

  • 每个变更有明确意图；
  • Agent 在边界内执行；
  • 系统提供可验证证据；
  • 人类拥有不可委托的判断与风险；
  • 每次生产结果都能反馈为下一次交付的能力增量。

当实现变得便宜，组织最昂贵的资产不再是代码，而是对正确方向、正确边界与正确结果的判断能力。

术语 定义
AI Native SDLC 将意图、知识、验证、治理与反馈重构为 Agent 可读取、可执行、可验证、可审计的研发系统
可信变更 带有意图、约束、实现、验证、责任和反馈的最小交付单元
Context Engineering 在正确时机提供完成任务所需高信号上下文，并管理其版本、权限和生命周期
Harness Engineering 模型外的工具、权限、沙箱、工作流、观测、评测与治理环境
Skill 使组织知识在执行时被一致应用的建议性控制
Hook 在工具调用或关键动作发生时允许、阻断或请求审批的确定性控制
Eval 用于比较 Agent/配置版本任务表现的可重复评估样本与评分机制
Trace 一次 Agent 任务从输入、上下文、模型、工具调用到输出与反馈的完整轨迹
